## OAuth and credential handling

- [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) defines HTTP authorization. Local stdio credentials/login behavior are not universally standardized by that HTTP flow.
- [OAuth native-app guidance](https://www.rfc-editor.org/rfc/rfc8252) and [OAuth security guidance](https://www.rfc-editor.org/rfc/rfc9700) explain browser authorization, authorization-code protection, short-lived access tokens, and protection of renewal credentials. Exchanging one permanent bearer token for another is not by itself protection against theft of the final token.
- A URL identifies a service/resource. The access token establishes permitted account/client access; the caller's IP is not the normal OAuth account identity. Credentials belong in the appropriate authentication channel, not URL query strings.
- [Environment variable semantics](https://zsh.sourceforge.io/Doc/Release/Parameters.html) and [shell startup files](https://zsh.sourceforge.io/Doc/Release/Files.html) distinguish a process's runtime environment from files used to populate it. A `.env` file only matters when loaded. Passing a variable reference does not remove the authenticating process's need to receive the value.
- Credentials can appear in arbitrary environment values, arguments, URLs, headers, or embedded commands. No generic detector proves all configuration safe to copy. The exact import policy needs approval and meaningful tests.
- New software installation does not necessarily remove/avoid old login caches. Fresh authentication requires wrapper-specific behavior.

### Credential names/references are not values

In the configuration draft, `EXAMPLE_API_KEY` is the destination variable name; `stored-entry-7` is an opaque reference within that server's encrypted credential context. The agent neither sends nor receives the value. Fetch's trusted backend privately retrieves the assigned credential and supplies it directly through the server's supported integration when needed. The exact handoff/key mechanism still needs design. Config editing changes a binding, not the secret. Fetch-managed secret input remains Settings-only or trusted automatic OAuth; values must not enter management GET/PATCH/MCP output, rejected-value errors or logs.

This protects the management boundary; it is not evidence that every arbitrary third-party tool returns no secrets. The current Playwright [config handler](https://github.com/microsoft/playwright/blob/a169686c61af856cd1434b4994ef9c3222ee1041/packages/playwright-core/src/tools/backend/config.ts) serializes the resolved config, **and central redaction exists**: [response serialization](https://github.com/microsoft/playwright/blob/a169686c61af856cd1434b4994ef9c3222ee1041/packages/playwright-core/src/tools/backend/response.ts) calls the [context's registered-secret/URL-parameter redactor](https://github.com/microsoft/playwright/blob/a169686c61af856cd1434b4994ef9c3222ee1041/packages/playwright-core/src/tools/backend/context.ts). Looking only at JSON serialization would incorrectly imply an established leak. Full coverage of arbitrary sensitive headers/storage-state and exact installed-version behavior has not been verified. A read-only tool annotation is not a confidentiality guarantee. Tool exposure/results still need step-2 review; do not silently rewrite all upstream results or assume an automatic policy is selected.

### Consequence for the pending configuration contract

D29 establishes scope, not a universal implementation. Revise the existing config API to cover supported individual-server settings through documented mappings: safe readable/writable fields/types, defaults, storage ownership, translation to flags/environment/config files or a documented native operation, and saved-versus-live/apply/restart behavior. Do not expose raw config files that may contain credentials or select arbitrary path writes. Fetch's encrypted credential file is Fetch-owned storage, not a format every upstream server knows how to read.

The previous three-field launch-only draft is incomplete and remains unapproved. Exact settings schemas/supported packages are proposals for the revised whole-contract review; no new route or live-reload promise is selected. D23's server GET currently reads saved metadata without provider/MCP probing; any live-native settings read needs explicit review. Agent-editable non-secret settings encoded as environment values need reconciliation with the existing Settings-only manual environment-value boundary, not a silent exception. Auth invalidation and restart effects need to account for the setting actually changed rather than automatically copying every launch-subset policy.

D30 later defers the broader native-settings normalization/mapping proposal beyond MVP. The source findings remain context; common launch-config is approved and no universal settings schema is an MVP requirement.

## Tool discovery, aggregation and cache boundaries — October 27

Dedicated read-only research checked current MCP2026-07-28 primary sources before step-2 planning. This is a researched revision, not a selected Fetch support-version/SDK. [Tool schema](https://modelcontextprotocol.io/specification/2026-07-28/schema#tool) requires name/inputSchema and permits title/description/outputSchema/annotations/icons/_meta. Keep JSON Schema structure rather than flattening arguments; object-root input versus potentially non-object output schemas matter. ### Restart acceptance versus completion — October 26

- [RFC 9110 section 15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) defines `202` as accepted but not completed. HTTP does not later replace that response with a second final response for the same request; a later request/status mechanism is needed to learn the outcome.
- [Microsoft's asynchronous request-reply guidance](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply) describes quick acceptance plus a status location for long-running operations, including terminal success/failure and optional progress. This informs completion reporting; it does not require Fetch to adopt Azure, a queue, or a separate process.
- Since normal restart waits for active calls, its duration can be unpredictable. The research recommendation was immediate acceptance plus status to avoid requiring the original connection to remain open throughout that wait. Held-open HTTP can still use nonblocking Rust/UI code; the distinction is how completion is reported.
- The user subsequently selected `202` plus separate completion with continuous loading, then chose `GET /api/v1/servers?id=...&restart_id=...` to monitor the particular attempt through server information. D20 subsequently approves the restart status schema, polling and readiness criteria on October 27. Exact ID representation/local job lifetime remain open; retention/recovery are deferred. ## Ordinary execution concurrency and cancellation — October27

Dedicated read-only research checked current/legacy primary sources before execution planning. MCP supports correlating concurrent requests by ID on a shared transport, but prescribes no universal concurrency cap, thread-safety/application-state isolation or 120-second call limit. These are Fetch policy choices. [Current stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) and [legacy timeout guidance](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle#timeouts) distinguish protocol mechanics from configurable request timeout/absolute-maximum recommendations.

Cancellation has no portable acknowledgement or guaranteed final reply. Receivers may be unable to cancel; current stdio prohibits further messages for a cancelled request. A local cancelled future, closed stream or elapsed client wait does not prove the tool stopped or external effects were undone. Current Streamable HTTP treats downstream disconnection as cancellation of that downstream request; do not describe all disconnects as semantically irrelevant. See [current cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation) and [legacy cancellation](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation).

Two product options were compared: (1) timeout merely detaches an ordinary HTTP waiter, retaining the upstream call for a possible terminal reply; abandoned actions continue and occupy capacity, but routine deadlines do not suppress final replies; (2) timeout forwards best-effort cancellation, matching recommended MCP timeout handling, but compliant suppression of a reply may leave work unresolved until explicit recovery. Neither guarantees stopping. Native MCP cancellation/disconnection must retain revision-correct handling under either option. Choice is not a selected policy or new API.

A one-call-per-server/no-queue design would bound unresolved-record count at one per installed server, while different servers run independently. It does not establish payload-byte/resource limits. Retain an uncertain reservation until terminal upstream RPC completion or confirmed managed-child exit; a local timeout/cancelled future alone is insufficient. If no terminal response arrives, existing explicit force-restart/Quit can recover local control without proving external effects stopped; D20 normal60/stop5/readiness30 rules remain selected. A shared wrapper/connection means shared provider credentials and application state, such as a browser page, not isolated sessions per Fetch caller. Keep other callers' identities/arguments/results out of busy/status/error data.

Maintained implementation comparison, source-only refreshed October27:

## Queued execution and tool timeout discovery — October27

Dedicated research and root primary-source checks confirm no standard discoverable timeout field in [current Tool](https://modelcontextprotocol.io/specification/2026-07-28/schema#tool)/ToolAnnotations or [legacy ToolExecution](https://modelcontextprotocol.io/specification/2025-11-25/schema#toolexecution), whose execution metadata describes task support. A timeout input/custom metadata field may use different units/defaults and cover only a sub-operation. Preserve it; do not infer or mutate a whole-call deadline. Client/SDK request settings are separate. [Current timeout guidance](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation#timeouts) recommends configurable per-request timeout plus an absolute maximum but sets no universal duration. A known documented integration limit could inform policy with allowance for receiving its final result; unknown fallback/overrides remain decisions.

For queues, use a single proposed per-server scheduler with active capacity C and waiting capacity Q, with unresolved forwarded work still occupying C. All admitted work follows the same order, and FIFO with C greater than one concerns start order, not completion. Resolve cancellation/deadline versus dispatch atomically, recheck current authority/server generation before forwarding and never hold the scheduler lock for a full RPC. A queued cancellation/expiry proves not_started. Separate queue waiting from dispatched execution time; never silently carry queued calls across restart generations. Proposed restart flush is an extension requiring user input, not a change approved by D51.

[Sender reserve/cancellation](https://docs.rs/tokio/1.54.1/tokio/sync/mpsc/struct.Sender.html) and [cancel-safe receive](https://docs.rs/tokio/1.54.1/tokio/sync/mpsc/struct.Receiver.html#method.recv) illustrate implementation constraints, not a selected Fetch dependency.
